# da_waydroid-apps

Declarative, data-driven provisioning of a curated Android app set into the local
**Waydroid** (LineageOS) container on the Surface desktop — plus a fully data-driven
**launcher layout** (hotseat "bottom bar" + home-screen workspace + folders) and **theme**
(dark mode + generated dark wallpaper).

Same engine contract as the other `da_*` desktop tools: `build.sh` (engine) + `build.json`
(data). Nothing is hardcoded in the engine — the app list, the launcher layout, folders,
theme, F-Droid endpoints, Waydroid data root and launcher DB are all read from `build.json`
or discovered at runtime.

## What it installs

`build.json → apps[]` (install manifest): Cloud-SuperApp (local x86_64 build) + from F-Droid
Acode, Amaze, FairMail, Mattermost, Element, Nix-on-Droid, Fossify Phone/Contacts/Messages.

## Launcher layout (data-driven)

`build.json → launcher{}` defines the whole layout; the engine renders it into Launcher3's
`favorites` DB (folders = `itemType 2`, hotseat = `container -101`, workspace = `container -100`):

- **Folders** — `Cloud IDE` = {Acode, Amaze}; `Cloud Comms` = {Element, Mattermost, FairMail, Fossify ×3}.
- **Hotseat (bottom bar)** — `Cloud-SuperApp · [Cloud IDE] · [Cloud Comms]`.
- **Home screen (workspace, 6-col grid)** — row 0: SuperApp; row 1: `[Cloud IDE]` Acode Amaze;
  row 2: `[Cloud Comms]` Element Mattermost FairMail Fossify-Messages.

A `folder:<id>` placed in both hotseat and workspace yields two independent instances (same
title + members). **To rearrange, edit `launcher.hotseat` / `launcher.workspace.cells` /
`launcher.folders` in `build.json` and re-run `./build.sh layout`** — no code changes. The
generator is `src/lib/gen-layout-sql.js` (single source of truth for the SQL).

## Theme (data-driven)

`build.json → theme{}`: `dark_mode` toggles Android night UI; `wallpaper` is generated by
`build.sh` (ImageMagick, pulled from nixpkgs on demand) as a dark gradient and set via
`cmd wallpaper`. Colours/size live in `build.json`.

## Pipeline

```bash
./build.sh lock      # resolve F-Droid suggestedVersionCode + nix-prefetch sha256 -> src/apps.lock.json
./build.sh build     # nix build the pinned APK set -> dist/apks/  (+ copy local cloud-superapp APK)
./build.sh check     # verify lockfile <-> build.json and that every APK is present
./build.sh install   # waydroid app install every APK             (needs a RUNNING session)
./build.sh layout    # render folders+hotseat+workspace into Launcher3 DB (needs session)
./build.sh theme     # dark mode + generated dark wallpaper        (needs session)
./build.sh status    # session + declared apps + built APKs + live hotseat/workspace
./build.sh ship      # lock(if missing) + build + install + layout + theme
./build.sh undock    # restore the most recent launcher.db backup
```

`install` / `layout` / `theme` require your Wayland session (Waydroid needs a running session).

## Reproducibility

`src/apps.lock.json` pins every remote APK to a versionCode + SRI `sha256`. `src/flake.nix`
fetches only those pinned, hashed URLs, so `nix build` is byte-reproducible on any machine.
`build.sh lock` is the only step that touches the network unpinned — re-run it to bump
versions (like `npm install` regenerating a lockfile).

## Dock seeding is schema-introspecting (not a hardcoded DB write)

The launcher DB filename is grid-dependent (`launcher_<cols>_by_<rows>.db`) so it is
globbed, never assumed. Before writing, the engine:
1. discovers the DB under the Waydroid data root,
2. backs it up to `dist/backups/`,
3. detects the live hotseat slot count,
4. resolves each app's LAUNCHER activity via `cmd package resolve-activity` (data-driven, not hardcoded components),
5. generates escaped SQL (`DELETE` hotseat + `INSERT` per slot), applies it with the launcher stopped, checkpoints WAL, relaunches, and verifies.

A bad edit can crash-loop the launcher; `./build.sh undock` restores the backup.

## Test

```bash
bash src/test/test.sh
```

Pure tests (schema, dock_order contiguity, core→ide→comms order, lockfile consistency, SQL
escaping + slot cap) run anywhere; the live test runs only when a Waydroid session is up.

## Note: Waydroid itself is not yet declarative

`waydroid` is installed on this host but is **not** in any NixOS/home-manager flake
(`grep -ri waydroid ~/git/unix` → nothing). This project provisions *into* Waydroid; making
`virtualisation.waydroid.enable` itself declarative in the Surface host config is a separate,
recommended follow-up.
